01 / Hash map

Hash map

Account state · UTXO index · Kademlia peer table

An Ethereum account (nonce, balance, storageRoot, codeHash) is conceptually keyed by address in a hash map before it's ever committed into a trie. Bitcoin's chainstate database is a hash index from outpoint (txid:vout) to unspent output, so checking "is this input still spendable" is O(1) instead of a chain scan. Kademlia-style peer tables key node IDs the same way, bucketed by XOR distance.

The interesting part isn't the average case — it's the adversarial one. A node's key space is partly attacker-chosen (anyone can pick which address or peer ID to send you), so a hash function with predictable collisions turns your O(1) map into an O(n) one under a targeted flood. That's why clients seed their hash functions randomly at process start rather than using a fixed table.

What to study

  • Chaining vs. open addressing
  • Average O(1) vs. adversarial worst-case O(n)
  • Seeded/keyed hashing against collision attacks
  • Read/write concurrency during block application

02 / Linked list

Linked list

Block-to-block chaining

The name is literal: every block header stores prevHash, the hash of the previous header — a singly linked list, traversed backward from tip to genesis. Appending a new block is O(1). There's no native forward pointer, so full nodes build a separate height→hash index for forward lookups; the chain itself doesn't need one.

The property that matters isn't traversal speed, it's tamper evidence: a block's hash is a function of its own contents plus prevHash, so editing anything in block N changes block N's hash, which no longer matches what block N+1 stored as its prevHash — and that mismatch propagates to every block after it. You can't silently splice the middle of the list.

One real limitation: it's not doubly linked and it's not even really a single list — it's the canonical path through a tree of blocks. Competing tips (forks) exist simultaneously; nodes pick the heaviest chain and treat the rest as orphaned.

What to study

  • prevHash reference, O(1) append
  • Backward-only traversal, no native index
  • Why tampering cascades forward
  • Forks: the "list" is really a tree's longest path

03 / Queue

Queue

Mempool intake · gossip message processing

Unconfirmed transactions arrive over the p2p network out of order and get buffered in the mempool before anyone decides what to do with them — that buffering is a queue. Network message handling (block/tx/inv gossip) is similarly queued so I/O and validation can run at different paces without one blocking the other.

In practice it's rarely pure FIFO: Bitcoin Core's mempool caps itself around 300MB by default and evicts the lowest-feerate entry when full, which is a bounded, priority-ordered queue wearing a queue's clothing. The extraction side of that priority ordering is the heap described next.

What to study

  • Strict FIFO vs. feerate-priority variants
  • Bounded capacity + eviction under memory pressure
  • Decoupling network I/O from validation

04 / Heap

Heap

Transaction selection by fee

Block space is scarce, so a miner or validator wants to fill it with the transactions that pay the most per byte — which is exactly a repeated extract-max over feerate. A binary max-heap gives O(log n) insert and O(log n) extract, so building a block from a mempool of tens of thousands of transactions stays fast.

Two details matter more than the average-case textbook version: stable ordering, because two transactions at the identical feerate shouldn't get reshuffled nondeterministically between runs (tie-break on arrival sequence); and priority updates, because a child-pays-for-parent bump or a replace-by-fee resubmission changes a transaction's priority after it's already in the heap, which needs an efficient decrease/increase-key rather than a full rebuild.

What to study

  • Min-heap vs. max-heap array layout
  • Stable tie-breaking on equal keys
  • In-place priority updates (CPFP, RBF)

05 / Merkle tree

Merkle tree

Transaction commitment

A block header carries one 32-byte Merkle root over every transaction in the block. That single hash lets anyone prove "transaction X is in block Y" with just log₂(n) sibling hashes, instead of shipping every transaction — which is what lets a light client verify inclusion against a header alone.

Root calculation pairs and hashes leaves level by level up to a single root. Bitcoin's specific rule for an odd node at any level is to duplicate it and hash it with itself — a shortcut that, combined with a transaction-malleability quirk, produced a real vulnerability (CVE-2012-2459: two different transaction lists could hash to the same root). Worth knowing not as trivia, but because it's the canonical example of an implementation detail in a "simple" structure causing a consensus bug.

What to study

  • Level-by-level root calculation
  • Odd-leaf duplication and its edge cases
  • Inclusion-proof construction (the sibling path)
  • Verification by re-hashing up to the root

06 / Merkle Patricia Trie

Merkle Patricia Trie

Ethereum world state, storage, receipts

Ethereum's state isn't a flat list, so a plain Merkle tree doesn't fit — it needs a key-value structure that's still content-addressed. The MPT is a radix-16 trie (one hex nibble per level) keyed by keccak256(address), built from three node kinds: leaf (remaining nibbles + value), branch (16-way fan-out), and extension (a shared nibble run collapsed into one node so you don't pay for 64 levels of single-child branches).

Every node is RLP-encoded and referenced by its own hash, so any subtree — a single account's storage, say — can be proven independently of the rest of the state; that's the mechanism behind eth_getProof. One encoding wrinkle worth knowing: a node under 32 bytes gets embedded inline in its parent rather than stored-and-referenced by hash, which is a real optimization, not an implementation detail you can ignore when hand-rolling one.

What to study

  • Hex-prefix encoding (leaf vs. extension, odd/even nibbles)
  • Path compression via extension nodes
  • Branch node's 16 slots + optional value
  • Inline vs. hash-referenced node encoding (32-byte rule)

07 / Sparse Merkle tree

Sparse Merkle tree

State proofs, L2 withdrawal proofs

A regular Merkle tree only has leaves for the items you inserted. A sparse Merkle tree instead has a fixed depth covering the entire key space — every possible key has a slot, whether or not something's stored there — which is what makes proving absence possible, not just presence.

The trick that keeps this from being an astronomically large tree in memory: every empty subtree at a given depth hashes to the same, precomputable "default hash" — you never build it, you just know what it would hash to. A membership proof is the usual sibling path to a real leaf; a non-membership proof is a sibling path showing the target key's slot resolves to a default (empty) hash instead of a stored value.

What to study

  • Precomputed default hashes per depth
  • Membership vs. non-membership proofs
  • Why fixed depth trades tree size for proof simplicity

08 / Bloom filter

Bloom filter

SPV filtering (BIP37) · log/event filtering

A Bloom filter answers "might this be relevant?" in constant space, at the cost of sometimes saying yes when the true answer is no — it never produces a false negative. Light (SPV) clients historically used one to ask a full node "send me anything touching these addresses" without listing every address outright (BIP37 — though the privacy this actually bought turned out to be weaker than intended, which is worth knowing as a cautionary case). Ethereum embeds a 2048-bit bloom in every block header and receipt over log topics/addresses, so eth_getLogs can skip blocks that provably don't match before doing the expensive exact check.

What to study

  • False-positive rate vs. bits / hash functions / item count
  • Bit-index computation from multiple hash functions
  • Sizing for a target false-positive rate
  • No false negatives, ever — only "definitely absent" is certain

09 / LRU cache

LRU cache

Trie-node cache, block cache

Nodes re-read the same hot state constantly — recently touched accounts, recently requested blocks — so an LRU cache sits in front of the trie/disk to avoid re-hitting storage for the working set. go-ethereum's trie node cache and Bitcoin Core's block/UTXO caches are concrete instances of exactly this.

Correct O(1) get/put needs both a hashmap (key → node) and a doubly linked list (recency order) — the hashmap alone can't tell you what's least recently used, and the list alone can't do O(1) lookup. Eviction removes the true tail of the list, not merely the oldest-inserted key, which is the detail that distinguishes LRU from a plain bounded FIFO.

What to study

  • Hashmap + doubly linked list combination
  • O(1) get/put, true least-recently-used eviction
  • Hard capacity ceiling — bounded memory is the point
  • Thread-safety when reads race writes

10 / Append-only log

Append-only log

Block files (blk*.dat) · database WAL

Bitcoin Core stores raw blocks as a sequence of length-prefixed records appended to blk*.dat files; the state databases underneath both clients keep a write-ahead log for the same reason databases always do — sequential appends are fast, and a crash mid-write can only ever corrupt the last record, never anything already flushed before it.

That guarantee only holds if every record is individually checksummed. A single file-level checksum can't tell you where corruption starts; a per-record checksum lets you replay from the beginning and stop cleanly at the first bad or truncated record, treating everything before it as a safe, readable prefix — no manual repair needed on restart.

What to study

  • Length-prefixed record framing
  • Per-record checksums, not per-file
  • Crash recovery: replay, stop at first bad record
  • Safe truncation of a torn tail write

11 / Graph

Graph

Peer-to-peer overlay network

Each node keeps a bounded set of peer connections — not a full view of the network — and gossips new blocks and transactions to its neighbors, who forward to theirs. The overlay is a graph, not a tree: there's no single propagation root, and multiple paths to the same node are normal (and useful — redundancy is what keeps the network resilient to any one dead peer).

What actually gets studied here isn't graph theory in the abstract, it's three concrete failure/success modes: whether the graph stays well-connected as nodes join and leave, how many hops (and how much wall-clock time) it takes for a new block to saturate the network — which is a real input into chain-tip races — and whether any node or cluster can end up partitioned, either accidentally or via a deliberate eclipse attack that isolates a victim behind attacker-controlled peers.

What to study

  • Bounded peer sets, not full-mesh
  • Gossip/flood propagation, hop count vs. time
  • Connectivity guarantees under churn
  • Partitions and eclipse attacks

Five to implement yourself

Ordered by how much machinery each one drags in. Do them in order — the heap reuses nothing from the Merkle tree, but the log exercise is easiest to get subtly wrong, so it's last on purpose. Reference implementations below are JavaScript for portability; the logic ports directly to any language with a hash function and a byte buffer.

1

Hash-linked block list

Proves you understand: why tamper-evidence falls out of hashing, not out of the list structure itself.

block-list.jsbuild add(), isValid()
class Block {
  constructor(index, data, previousHash) {
    this.index = index;
    this.timestamp = Date.now();
    this.data = data;
    this.previousHash = previousHash;
    this.hash = this.computeHash();
  }
  computeHash() {
    return sha256(`${this.index}${this.timestamp}${JSON.stringify(this.data)}${this.previousHash}`);
  }
}

class Chain {
  constructor() { this.blocks = [this.genesis()]; }
  genesis() { return new Block(0, "genesis", "0".repeat(64)); }

  add(data) {
    const prev = this.blocks.at(-1);
    const block = new Block(prev.index + 1, data, prev.hash);
    this.blocks.push(block);
    return block;
  }

  // walk the whole chain: does every stored hash match
  // its own recomputed hash, and its neighbor's prevHash?
  isValid() {
    for (let i = 1; i < this.blocks.length; i++) {
      const cur = this.blocks[i], prev = this.blocks[i - 1];
      if (cur.previousHash !== prev.hash) return false;
      if (cur.hash !== cur.computeHash()) return false;
    }
    return true;
  }
}
2

Merkle tree with proof generation + verification

Proves you understand: that a proof is nothing more than "the siblings you'd need to recompute the root," and that verification is a one-way replay of the same folding.

merkle.jsroot(), proof(), verify()
function merkleRoot(leaves) {
  let level = leaves.map(sha256);
  if (level.length === 0) return sha256("");
  while (level.length > 1) {
    const next = [];
    for (let i = 0; i < level.length; i += 2) {
      const left = level[i];
      const right = level[i + 1] ?? left; // odd tail: duplicate
      next.push(sha256(left + right));
    }
    level = next;
  }
  return level[0];
}

function merkleProof(leaves, index) {
  let level = leaves.map(sha256), idx = index;
  const proof = [];
  while (level.length > 1) {
    const next = [];
    for (let i = 0; i < level.length; i += 2) {
      const left = level[i], right = level[i + 1] ?? left;
      if (i === idx || i + 1 === idx) {
        const isLeft = idx % 2 === 0;
        proof.push({ hash: isLeft ? right : left, isLeft: !isLeft });
      }
      next.push(sha256(left + right));
    }
    idx = Math.floor(idx / 2);
    level = next;
  }
  return proof;
}

function verifyProof(leaf, proof, root) {
  let hash = sha256(leaf);
  for (const step of proof) {
    hash = step.isLeft ? sha256(step.hash + hash) : sha256(hash + step.hash);
  }
  return hash === root;
}
3

Fee-prioritized transaction queue

Proves you understand: array-backed binary heaps, and why "highest fee first" needs a tie-break to be deterministic.

fee-heap.jspush(), pop() — max-heap
class FeeHeap {
  constructor() { this.items = []; this.seq = 0; }

  push(tx) {
    const node = { tx, fee: tx.fee, seq: this.seq++ };
    this.items.push(node);
    this.#bubbleUp(this.items.length - 1);
  }

  pop() {
    const top = this.items[0];
    const last = this.items.pop();
    if (this.items.length) {
      this.items[0] = last;
      this.#bubbleDown(0);
    }
    return top?.tx;
  }

  // higher fee wins; equal fee, earlier arrival wins — stable order
  #higher(a, b) { return a.fee !== b.fee ? a.fee > b.fee : a.seq < b.seq; }

  #bubbleUp(i) {
    while (i > 0) {
      const p = (i - 1) >> 1;
      if (!this.#higher(this.items[i], this.items[p])) break;
      [this.items[i], this.items[p]] = [this.items[p], this.items[i]];
      i = p;
    }
  }

  #bubbleDown(i) {
    const n = this.items.length;
    while (true) {
      let best = i; const l = 2 * i + 1, r = 2 * i + 2;
      if (l < n && this.#higher(this.items[l], this.items[best])) best = l;
      if (r < n && this.#higher(this.items[r], this.items[best])) best = r;
      if (best === i) break;
      [this.items[i], this.items[best]] = [this.items[best], this.items[i]];
      i = best;
    }
  }
}
4

LRU cache with strict capacity

Proves you understand: that O(1) recency tracking needs order-preserving storage, not just a lookup table — Map's insertion order does the linked-list job for free in JS.

lru.jsget(), put() — O(1)
class LRUCache {
  constructor(capacity) {
    this.capacity = capacity;
    this.map = new Map(); // Map preserves insertion order
  }

  get(key) {
    if (!this.map.has(key)) return undefined;
    const value = this.map.get(key);
    this.map.delete(key);
    this.map.set(key, value); // re-insert = mark most recently used
    return value;
  }

  put(key, value) {
    if (this.map.has(key)) {
      this.map.delete(key);
    } else if (this.map.size >= this.capacity) {
      const oldest = this.map.keys().next().value; // true LRU: map head
      this.map.delete(oldest);
    }
    this.map.set(key, value);
  }
}
5

Append-only block file with checksums + partial-write recovery

Proves you understand: why per-record framing, not per-file, is what makes crash recovery a read loop instead of a repair tool.

append-log.jsappendRecord(), readValidRecords()
// record layout: [4-byte length][4-byte crc32][payload]

function appendRecord(fd, payload) {
  const header = Buffer.alloc(8);
  header.writeUInt32BE(payload.length, 0);
  header.writeUInt32BE(crc32(payload), 4);
  fs.appendFileSync(fd, Buffer.concat([header, payload]));
}

function readValidRecords(fd) {
  const buf = fs.readFileSync(fd);
  const records = [];
  let offset = 0;

  while (offset + 8 <= buf.length) {
    const length = buf.readUInt32BE(offset);
    const crcStored = buf.readUInt32BE(offset + 4);
    const start = offset + 8, end = start + length;

    if (end > buf.length) break; // torn tail write — stop, don't throw
    const payload = buf.subarray(start, end);
    if (crc32(payload) !== crcStored) break; // corrupt record — stop here too

    records.push(payload);
    offset = end; // this is the safe recovery/truncation point
  }
  return { records, safeLength: offset };
}
