The map

A block is a header (small, fixed-shape, cheap to verify) plus a body (large, variable, expensive to verify) — and almost every interesting question about a blockchain's integrity is really a question about how the header commits to the body, and how nodes agree on which sequence of headers is canonical.

01 / Structure

Anatomy of a block

Header vs. body, and what the block hash actually covers

A block splits into two parts with very different cost profiles. The header is small and fixed-shape — a few hundred bytes, cheap enough that every node, including light clients, can hold every header ever produced. The body is the transaction list — large, variable-length, and expensive to download and re-execute.

The header's fields: version (protocol/format flag), previous block hash (the parent link), transaction Merkle root (commits to the body), state root (commits to the account/world state after this block executes), timestamp, height (Bitcoin stores it implicitly via chain position; Ethereum stores it explicitly in the header), and consensus-specific fields — nonce and difficulty target under proof-of-work, or proposer/slot/validator signature data under proof-of-stake.

The block hash — the thing that becomes the next block's previous block hash — is the hash of the header only, never the body directly. That's the whole trick: because the header contains the Merkle root, hashing ~100 bytes of header transitively commits to gigabytes of transactions. Change one transaction and the root changes, which changes the header, which changes the block hash.

What to study

  • Why header and body have different verification costs
  • Block hash = H(header), not H(all transactions)
  • Which fields are consensus-specific vs. universal
  • Why light clients only ever need headers

02 / Chain linkage

Genesis block, height, hash & parent-child relationships

How individual blocks become "the chain"

The genesis block is block 0 — the one block with no parent. Its previous block hash field is hardcoded to all zeros (or another agreed sentinel), and it's baked into the client software rather than received over the network; every node has to already agree on it before consensus can mean anything.

Height is a block's distance from genesis, measured in hops along prevHash pointers. It's a derived quantity, not an independent source of truth — a block doesn't get to declare "I am height 500,000" and have that be trusted; a node computes height by walking backward from a block to genesis and counting. (Ethereum stores height in the header as a convenience and a sanity check, but the chain of hashes is still what's authoritative.)

Block hash is the identity of a block — the SHA-256 (or Keccak-256) of its header, as covered in the section above. Parent-child is just: child's prevHash field equals parent's block hash. Follow that pointer backward from any tip and you eventually reach genesis; that backward walk is the entire mechanism, and it's why the whole structure is sometimes described as a singly linked list that only supports backward traversal.

What to study

  • Genesis has no parent — it's trusted by convention, not proven
  • Height is derived by walking, not stored as ground truth
  • Parent-child = child.prevHash == parent.blockHash
  • No forward pointers — full nodes build a separate height→hash index

03 / Commitments

Transaction root, state root & commitment verification

How a 32-byte field vouches for gigabytes of data

Both roots are the same idea applied to different data. The transaction Merkle root commits to the ordered list of transactions in this block's body — a Merkle tree over the transactions, root only. The state root commits to the entire account/world state after this block's transactions have executed — in Ethereum, the root of a Merkle Patricia Trie over every account's balance, nonce, code, and storage.

Commitment verification is always the same shape: recompute the root from the raw data you actually have, and compare it against the value stored in the header. If a single byte of a transaction changed, or a single account's balance is wrong, the recomputed root won't match — you don't need to inspect the whole dataset to know something's off, only the root.

This is what makes light clients possible: a client holding only headers can accept a Merkle proof — a transaction plus its log₂(n) sibling hashes — and verify inclusion against the header's root without ever downloading the rest of the block. The same logic applies to state: a light client can verify "this account has this balance" against just the state root, given the right proof path.

What to study

  • Tx root commits to the block body; state root commits to post-execution state
  • Verification = recompute, then compare — never trust a claimed root
  • Merkle proofs let you verify a leaf without the whole tree
  • A state root mismatch means the block claims a state transition it didn't earn

04 / Consensus

Block validation order & deterministic rejection rules

The sequence every honest node runs, in the same order, to the same verdict

Validation is ordered cheapest-and-most-decisive first, so a malformed or fraudulent block gets rejected before a node spends CPU on anything expensive. A typical order: (1) structural checks — does the block parse, is it under the size limit; (2) header checks — does the proof-of-work hash meet the difficulty target (or is the proposer's signature valid under PoS), is the timestamp within allowed drift, does prevHash point at a block the node actually has; (3) transaction Merkle root check — recompute from the body, compare to the header; (4) per-transaction validation — signatures valid, no double-spends, nonces sequential, fees/gas sufficient; (5) state transition — execute every transaction, recompute the state root, compare to the header; (6) consensus-specific checks — cumulative difficulty/weight, finality votes, slashing conditions.

The word that matters is deterministic: given the same block and the same prior chain state, every honest node must reach the exact same accept/reject verdict, every time. That rules out floating-point arithmetic (rounding differs across hardware), wall-clock-dependent logic beyond a bounded, protocol-defined drift window, and any iteration order that isn't fully specified — anything that could make two honest nodes disagree about a state root is a consensus bug waiting to happen, not an implementation detail.

Rejection is deterministic too: the first failing check stops validation immediately. A node doesn't execute transactions from a block whose Merkle root doesn't even match — that would be wasted work in the honest case, and a denial-of-service vector in the adversarial one.

What to study

  • Cheap, structural checks run before expensive execution
  • Every honest node must reach the identical verdict
  • No floats, no unbounded clock trust, no unordered iteration
  • First failing check short-circuits the rest

05 / Consensus

Forks, competing blocks & canonical chain selection

What happens when two valid blocks exist at the same height

Network latency guarantees that two miners (PoW) or two validators (PoS) can each produce a valid block extending the same parent at roughly the same time. Both blocks are individually valid — neither breaks any rule — so the protocol can't reject either one on its own merits. This is a fork: the block tree has two tips at the same height, and different peers may see either one first.

A fork-choice rule is what breaks the tie deterministically. Bitcoin's rule is commonly summarized as "longest chain," but the precise rule is most cumulative proof-of-work — total expended difficulty, not block count, because a shorter chain of harder blocks can outweigh a longer chain of easier ones. Ethereum post-Merge uses LMD-GHOST (latest-message-driven greedy heaviest-observed subtree), weighted by validator attestations rather than computational work.

Once one branch pulls ahead — more work, or more attestation weight — nodes converge on it as canonical, and the abandoned branch's blocks become orphans (Bitcoin) or, historically, uncles (Ethereum pre-Merge, which gave small rewards for referencing them). Their transactions weren't wrong, they just lost the race — which is why those transactions typically return to the mempool for possible inclusion in a later block.

What to study

  • Both competing blocks can be individually valid
  • "Longest chain" is shorthand — the real rule is heaviest chain
  • LMD-GHOST vs. cumulative proof-of-work as fork-choice rules
  • Orphaned blocks' transactions return to the mempool

06 / Consensus

Chain reorganization, state rollback & re-application

What a node does when its local tip loses the fork-choice race

A node builds its state incrementally, applying each block's transactions as it arrives. If that node's chosen tip later turns out to be the losing side of a fork — a competing branch overtakes it in weight — the node has to switch. That switch is a chain reorganization (reorg): find the common ancestor (the fork point), roll back state changes from the abandoned blocks in reverse order down to that ancestor, then re-apply the new branch's blocks in order, from the ancestor up to the new tip.

Rollback isn't a special undo log in most designs — it's usually achieved by keeping enough historical state (or being able to recompute it) to reset to the fork point, then re-executing forward. Depth matters enormously: a 1-block reorg is routine and near-costless; a 100-block reorg would mean re-deriving a huge amount of state and is treated as a near-catastrophic event on a mature chain, because it implies the fork-choice rule was wrong for a long time before anyone noticed.

Two practical consequences worth internalizing: transactions in the abandoned blocks aren't gone, they go back into the mempool and can be re-included in a later block if still valid; and any application built on top (an exchange crediting a deposit, say) needs to wait for enough confirmations that a reorg deep enough to reverse the relevant block becomes acceptably unlikely — which is exactly the finality question in the next section.

What to study

  • Reorg = find common ancestor, roll back, re-apply
  • Reorg depth vs. cost — 1 block is routine, 100 is catastrophic
  • Orphaned transactions return to the mempool, not deleted
  • Why downstream systems wait for confirmations before acting

07 / Consensus

Probabilistic versus deterministic finality

When can you actually treat a block as irreversible

Probabilistic finality (Bitcoin, and Nakamoto-consensus PoW chains generally) never reaches certainty — it's a confidence curve. Every additional confirming block on top of yours means an attacker would need to out-produce the entire honest network from that point on, which gets exponentially less likely with depth. "6 confirmations" is a convention, not a threshold with a hard guarantee behind it: it's the depth at which the reorg probability is considered negligible for most purposes, not zero.

Deterministic (absolute) finality (Tendermint-style BFT chains, and Ethereum's Casper FFG layered on top of LMD-GHOST) works differently: once a supermajority of validators — typically two-thirds by stake — sign off on a checkpoint, reverting it isn't just improbable, it's economically enforced to be nearly impossible: doing so requires provably violating a slashing condition, and the validators responsible lose a large fraction of their stake. Ethereum actually has two tiers — a block is first justified, then finalized once the next checkpoint is also justified, roughly two epochs (~12.8 minutes) later.

The practical difference: under probabilistic finality, "final" is a risk tolerance you choose (how many confirmations is enough for this transaction's value); under deterministic finality, "final" is a specific, discrete event a node can point to and say it already happened.

What to study

  • Confirmation depth as a decaying, never-zero risk curve
  • Slashing as what makes deterministic finality "absolute"
  • Justified vs. finalized checkpoints in Ethereum
  • Choosing confirmation counts by transaction value, not habit

Probabilistic · e.g. Bitcoin

Risk decays, never hits zero

Security scales with confirmations and honest hashpower. "Final" is a threshold you choose based on value at risk.

Deterministic · e.g. Ethereum PoS, Tendermint

Risk drops to zero at a checkpoint

Check your understanding

Ten questions, ordered to follow the sections above. Try answering before you expand each one.

Q1Why is the block hash computed only over the header, not over the header plus every transaction?

Because the header already contains the transaction Merkle root, which is itself a commitment to every transaction in the body. Hashing the header transitively commits to the whole body without the block hash function ever touching the raw transaction bytes. This keeps the block hash cheap to compute and re-verify (a few hundred bytes) regardless of whether the body holds 10 transactions or 10,000.

Q2A peer tells your node "the chain tip is at height 900,000." Should you trust that number directly?

No. Height isn't an independently verifiable fact you can take on say-so — it's derived by walking prevHash pointers back to genesis and counting hops (or, in Ethereum, cross-checked against the header's stored height field as you validate each block along the way). A node should request the actual chain of headers and derive height itself rather than trusting a claimed value.

Q3What specifically breaks if genesis had a parent, i.e. a non-zero previous block hash pointing somewhere real?

It would no longer be genesis — by definition, genesis is the block with no parent, the anchor every node hardcodes and agrees on out of band before any consensus rule can apply. If it pointed at another block, that block would become the true root of trust, and you'd need to ask the same "how do we agree on this without a parent" question one level further back. The chain has to bottom out somewhere that isn't derived from the protocol itself.

Q4A light client wants to verify that a specific transaction is in block N, without downloading the whole block. What does it need, and what does it check?

It needs the transaction itself plus its Merkle proof — the log₂(n) sibling hashes along the path from that transaction's leaf up to the root. It recomputes the root by hashing the transaction up through those siblings, then compares the result to the transaction Merkle root already stored in block N's header (which the light client holds, since headers are cheap). A match proves inclusion; it never needed the other transactions.

Q5Why does state-root verification happen after per-transaction validation and execution, rather than before?

The state root commits to state after this block's transactions run — you can't recompute it without first executing the transactions in order. And execution itself is only meaningful once you already know the transactions are individually well-formed (valid signatures, correct nonces, no double-spends), which is why per-transaction checks come first. Doing it in the reverse order would mean executing possibly-invalid transactions, wasting work and opening a cheap denial-of-service vector.

Q6Why does block validation reject on the first failing check instead of running all checks and reporting every problem?

Two reasons. First, cost: later checks (full transaction execution, state root recomputation) are far more expensive than earlier ones (structural parsing, header format), so short-circuiting avoids wasting CPU on a block that's already known-invalid. Second, security: an adversary who can force a node to always run the full, expensive pipeline — even on garbage blocks — has a cheap way to burn victim CPU. Rejecting immediately at the first failure closes that off.

Q7Two miners each broadcast a valid block extending the same parent at the same height. Is one of them wrong?

No — both can be entirely valid under every consensus rule; this is exactly what a fork is. Validity is a property of a single block against the rules; canonicity is decided separately, afterward, by the fork-choice rule (most cumulative work, or LMD-GHOST weight) once the network has had time to build on one branch more than the other. Being "wrong" and being "orphaned" are different things — an orphaned block didn't break any rule, it just lost the race.

Q8Why is "most cumulative proof-of-work" more accurate than "longest chain" as a description of Bitcoin's fork-choice rule?

Because difficulty isn't constant — blocks can be mined at different difficulty targets over time (and, in principle, an attacker chain could contain more blocks but represent less total computational effort if those blocks were mined at lower difficulty). The rule that actually matters is the sum of expended work across the chain, not the count of blocks. "Longest chain" is the common shorthand because in practice, at stable difficulty, more work and more blocks track together — but the rule itself is about weight, not length.

Q9After a 2-block reorg, what needs to happen to the transactions that were in the abandoned blocks?

They aren't discarded outright — a node re-checks each one against the new canonical state (since state has changed, some may now be invalid, e.g. a double-spend that already landed in the new chain) and returns the still-valid ones to the mempool, where they're eligible for inclusion in a future block. Silently dropping them would mean a user's already-broadcast, still-legitimate transaction just vanishes, which is a worse failure mode than re-queuing it.

Q10An exchange wants to credit a large deposit only once it's "safe." How should it decide, and does that decision look different on a PoW chain versus a PoS chain with finality?

On a probabilistic-finality chain (PoW), there's no single correct number — the exchange picks a confirmation depth where the residual reorg probability is acceptable given the deposit's value, accepting that the risk never hits exactly zero. On a deterministic-finality chain (PoS with Casper FFG-style checkpoints), the exchange can instead wait for the specific block to be finalized — a discrete, checkable event — after which reversal would require provable, slashable validator misbehavior rather than just bad luck. The PoS case lets the exchange wait for an actual guarantee instead of tuning a risk threshold.
